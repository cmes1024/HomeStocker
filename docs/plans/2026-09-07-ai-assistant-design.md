# AI 对话助手 — 设计文档（V1）

> 日期：2026-09-07 | 状态：需求讨论已收敛，待转 OpenSpec change / 进入实现
> 关联文档：`docs/PRD-家庭物资管理小程序.md`（v1.2）、`docs/技术架构-家庭物资管理小程序.md`（v1.1）

---

## 1. 背景与目标

### 1.1 背景
HomeStocker 是一款以「家庭」为单位的物资管理微信小程序，现有产品文档与原型已覆盖传统的页面交互（首页 / 物资列表 / 详情 / 添加 / 家庭管理）。

本次讨论希望新增一条 **AI 对话通道**：用户通过自然语言（文字/语音）管理家庭物品，同时**完整保留传统页面交互**，两条通道读写同一份数据、互相可见。

### 1.2 V1 目标（明确收敛）

| 维度 | 决策 |
|------|------|
| V1 能力范围 | **查询 + 简单录入**（不做全量 CRUD、批量、主动建议） |
| 查询 | 查物资、查临期/过期 |
| 录入 | 一句话记录一条物资（名称/数量/单位/位置/保质期/备注） |
| 对话入口 | 首页悬浮按钮 + 半屏面板 |
| 数据一致性 | 对话写入与页面写入走同一份数据库 |

## 2. 技术选型与决策

### 2.1 三个候选技术的定位辨析

| 技术 | 本质 | 结论 |
|------|------|------|
| LangGraph (CLI) | Agent 编排框架（有状态 LLM 智能体） | **采用**：作为「脑子 + 手脚」，负责意图理解 → 工具调用 → 自然语言回复 |
| openRAG | RAG 检索栈（多个同名项目：langflow-ai/openrag、linagora/openrag 等） | **不采用**：解决「文档知识库问答」，非本场景核心 |
| oneRAG | RAG 后端框架（Python/FastAPI，可插拔向量库/LLM，OpenAI 兼容 API） | **暂不采用**：结构化数据增删改查走工具调用，非文档检索 |

> 关键判断：家庭物资管理是**结构化数据的增删改查**（function-calling 问题），不是文档检索（RAG）问题。RAG 留到出现语义搜索 / 知识库需求时再评估（触发条件见 §8）。

### 2.2 最终选型

| 层 | 选择 |
|----|------|
| Agent 技术栈 | **LangChain（模型/工具/消息抽象）+ LangGraph（状态编排）** |
| Agent 服务形态 | FastAPI 运行 LangGraph 图（不强制依赖 LangGraph Platform/Cloud） |
| LLM 底座 | 国产模型（DeepSeek / 通义千问 / GLM / 混元），做成可插拔封装 |
| 部署路径 | 路径 A：云函数中转（见 §6.1） |
| RAG | V1 不引入 |

> 说明：LangGraph 是 LangChain 团队出品的**编排层**，构建在 LangChain 之上，二者不是二选一。本架构中：
> - **LangChain** 负责 LLM 封装（国产模型集成包）、tool schema 定义、消息对象、Prompt（`classify` 意图判断等）。
> - **LangGraph** 负责 `StateGraph` 状态图、节点/边流转、State 管理、checkpointer 多轮对话记忆。
>
> 因此准确表述为「LangChain + LangGraph 作为 Agent 技术栈」。

## 3. 总体架构

```
微信小程序（原生，保留全部现有页面）
├── 传统页面（不变）：首页 / 物资列表 / 详情 / 添加 / 家庭管理 ─┐
└── AI 对话半屏面板（新增）                                      │ 读写同一份数据库
        │ 文字 / 语音(STT 后转文字)                              │
        ▼                                                        │
   云函数中转（注入 openId / userId）                             │
        ▼                                                        │
   LangChain + LangGraph 服务（FastAPI 跑图）                      │
        │ 调用 4 个 tool                                          │
        ▼                                                        ▼
   云开发文档数据库（families / items / users / shopping_list / ...）
```

**核心原则**：对话与传统页面是同一数据的两种入口，不引入第二套存储、不做数据搬运。

## 4. V1 范围与交互模型

### 4.1 入口

首页右下角**常驻悬浮按钮**，点开弹出**半屏对话面板**；不占用底部导航，传统页面动线不变。

### 4.2 能力清单

| 能力 | 用户话术示例 | Agent 行为 |
|------|-------------|-----------|
| 查物资 | 「家里还有牛奶吗」「冰箱里有什么」「米还有多少」 | `search_items`，按名称/位置/分类查当前家庭，回列表卡片 |
| 查临期 | 「哪些快过期了」「最近有什么要赶紧吃」 | `list_expiring`，按 `expireDate` 查临期/过期，回提醒卡片 |
| 简单录入 | 「帮我记一下：刚买了 2 瓶牛奶，放冰箱冷藏，9 月 20 日过期」 | 解析字段 → `add_item` 写入 → 回「已记录」+ 卡片 |

### 4.3 交互决策（已定）

1. **写操作不打断用户**：录入直接执行，回「已记录 ✅」卡片；卡片可点击跳详情页编辑/撤销（不做录入前确认弹窗）。
2. **对话默认作用于当前家庭**：读 `users.currentFamilyId`；V1 不支持在对话内切换家庭（靠顶部家庭切换栏切换）。
3. **数据一致性**：对话与页面读写同一份数据库，聊完回到列表页/首页立即可见。

## 5. Agent 图结构（LangGraph）

V1 采用**单 Agent + 工具循环**，不做多 Agent 拆分（YAGNI）。

### 5.1 State

| 字段 | 说明 |
|------|------|
| `messages` | 对话历史 |
| `userId` | 鉴权得到的用户 ID（同 openId） |
| `familyId` | 当前家庭 ID（由 `userId` 解析） |
| `toolResults` | 工具执行结果 |

### 5.2 图节点（3 个 + 工具循环）

> 实现时把「classify」与「respond」合并为单一 `agent` 节点（标准 ReAct 循环）：
> 一次 LLM 调用既决定调工具，也能在拿到工具结果后直接产出最终答复，
> 避免单步工具调用导致多步意图（如先 `get_current_family` 再 `add_item`）中断。

```
load_context ──▶ agent ⇄ call_tool
  (解析当前家庭      (LLM 带工具：意图判断 / 工具结果 → 自然语言回复)
   + 家庭位置/分类)       │
                         └─ 有 tool_calls 则执行工具后回到 agent，否则 END
```

**关于日期注入**：系统提示词中注入「今天的日期（含星期）」，
使模型能把「下周三」「三天后」等相对日期换算成绝对 `expireDate`（实测必要）。

### 5.3 工具（4 个）

| 工具 | 参数 | 映射字段 |
|------|------|---------|
| `get_current_family` | 无 | `users.currentFamilyId` → `families` |
| `search_items` | query, category?, location?, status? | `items`（按 `familyId` 过滤） |
| `list_expiring` | days=3 | `items.expireDate` + `items.status` |
| `add_item` | name, quantity, unit, category, location, expireDate?, notes? | `items` 新增一条 |

### 5.4 录入解析规则

1. 用 LLM function-calling 把一句话转成结构化字段。
2. `category` / `location` 若不在家庭预设里，自动写入 `families.categories` / `families.locations` 并提示用户。
3. 缺失的必需字段（数量、位置）由 Agent **追问**，不瞎填。
4. 相对日期（「9 月 20 日」「下周五」「三天后」）→ 绝对 `expireDate`；处理跨年推断（今天已过该日期则默认次年）。

## 6. 关键设计与难点

### 6.1 鉴权与部署路径（路径 A）

- Agent 服务独立部署（FastAPI 跑 LangGraph）。
- 小程序不直连 Agent，而是通过**云函数中转**：云函数天然拿到 `openId`，转发时注入 `userId`，Agent 据此解析 `currentFamilyId`。
- 端上不传用户身份 → 防伪造、复用云开发登录态、零新增鉴权成本、规避小程序「合法域名 + ICP 备案」门槛。
- 后续演进：Agent 逻辑稳定且有备案域名后，可平滑过渡到路径 C（直连），改善流式体验。

### 6.2 流式输出

- 小程序 `wx.request` 支持 `enableChunked` 分块接收，但云函数对 SSE 透传支持有限。
- **V1 采用整段返回（非流式）**，Agent 回复通常 1–3 秒可接受；流式放到 V1.1 直连阶段。

### 6.3 语音输入

- 用微信官方「同声传译」插件（WechatSI）做语音转文字（免费、无需自建 ASR），转成文字后再进 Agent。
- V1 不做端到端语音理解 / 多模态。

### 6.4 缓存一致性

- 现有页面有 30 分钟本地缓存。对话写入后必须失效缓存，否则「聊完列表不更新」。
- 方案：对话写库成功后递增数据版本号 / 清空物资缓存，页面 `onShow` 检测版本变化后重新拉取。

### 6.5 错误处理（兜底原则）

| 场景 | 处理 |
|------|------|
| LLM 拒答/跑题 | `classify` 判非业务意图，友好回退「我可以帮你查物资、查临期、记一笔」+ 示例话术 |
| 工具失败/超时 | 统一回「这个操作没成功，去列表页看看」，不吐技术报错 |
| 字段不全且用户不耐烦 | 连续 2 轮追问仍缺字段 → 放弃，给结构化表单卡片，引导用户打开传统添加页补全 |
| 幻觉防护 | 所有写操作必经 `add_item` 工具，字段做白名单/枚举校验，LLM 无法直接写库 |

## 7. 落地路径与里程碑

### 7.1 MVP（最小链路）

1. LangGraph 图 + 4 个 tool（先接 mock 数据，再切云开发真实数据）。
2. 云函数中转（注入 openId/userId）。
3. 小程序对话半屏面板跑通两句：一句「记一笔」、一句「哪些快过期了」。

### 7.2 演进（V1.1+）

| 阶段 | 内容 |
|------|------|
| V1.1 | 流式输出（直连路径 C）、对话内跨家庭切换、批量录入、主动建议 |
| 后续 | 语义搜索（触发 RAG 评估）、消耗统计、智能采购建议 |

---

## 8. RAG 的触发条件（何时再评估 openRAG / oneRAG）

当出现以下需求时，重新评估引入向量检索（可优先考虑 oneRAG 的「OpenAI 兼容 API + 可插拔向量库/LLM」，或 openRAG 的可视化编排）：

- 跨条目语义搜索（如「找我那个蓝色的保温杯」，而条目名可能是「水杯」）。
- 检索非结构化内容：OCR 小票原文、自由文本备注、产品说明、家庭历史/偏好。
- 需要把历史对话 / 家庭知识沉淀为可检索的记忆库。

在此之前，一律用结构化 tool-calling + 数据库索引解决，避免过早引入重组件。
