# 家庭会员增值方案 — 落地步骤与优先级

> 目录：[`README.md`](./README.md) · [`方案.md`](./方案.md) · [`数据模型.md`](./数据模型.md)

本文档把方案拆成 **3 个阶段**，每个阶段都可独立上线、独立验收、独立看到效果。
不追求一次性全部做完，**先拿最小闭环验证付费意愿，再迭代**。

---

## 总览

| 阶段 | 目标 | 周期 | 上线后可衡量指标 |
|------|------|------|-----------------|
| **P0 · 节流 + 占位** | 给 AI V1 上免费额度，让模型成本可控；在 UI 上露出会员入口但不接真支付 | 1 周（~3 人日） | AI 调用成本下降幅度；首页/家庭页会员入口点击率 |
| **P1 · 付费闭环** | 跑通建单 → 支付 → 回调延长订阅 → 门控放行的完整链路；AI V2 上线同步按会员专享卖 | 2 周（~8 人日） | 免费→付费转化率；首单量；续费率（上线 30 天后看） |
| **P2 · 精细化运营** | 容量 / 主题 / 导出等差异化；优惠券 / 体验赠送；成本看板；续费自动化 | 1 个月（2~3 周） | ARPU 提升；续费率提升；毛利稳定 > 70% |

---

## P0 · 节流 + 占位（最快本周上线）

> 目标：先把**模型成本支出**控制住，同时在真实用户里测「大家点不点会员按钮」。  
> 即使完全不做 P1/P2，P0 做完也能显著减少「被免费用户把 API 费用刷爆」的风险。

### P0 任务清单

| T-ID | 任务 | 产出物 | 验收标准 |
|------|------|--------|----------|
| P0-1 | 建 `subscriptions` / `usageLogs` 两集合 + 安全规则 + 索引 | 控制台手动建好；或在云函数 `ensureDefaults` 里首次调用自动 `createCollection` | 参考 [数据模型.md §2~3](./数据模型.md#2-新增集合总览) |
| P0-2 | 实现 `_shared/gatekeeper.ts` 的精简版（只做 2 个 feature） | `checkEntitlement({ familyId, openid, feature: 'aiCapture'|'aiAssist', consume })` | 内部查表（FEATURE_MATRIX）+ 查 `usageLogs` 做 count，返回 `{ allowed, reason, remaining }` |
| P0-3 | `family.create` / `family.join` 里写 `subscriptions` 的免费默认档 | 在 `cloudfunctions/family` 对应 action 成功后 upsert：`{ plan: 'free', status:'active', startAt: now, endAt: MAX_SAFE_INTEGER, source:'default' }` | 新家庭建完后 `subscriptions.doc(familyId).get()` 能读到 free |
| P0-4 | 对存量家庭跑一次脚本补 `subscriptions` 免费档 | 临时云函数或控制台批量导入 | 所有 `families._id` 都能在 `subscriptions` 中命中 |
| P0-5 | `cloudfunctions/ai/extract` 开头接入门控 | 如果该家庭 BYOK 可用 → 直接放行；否则按 openid × 日 5 次限 | 超过额度返回 `{ code: 'UPGRADE_REQUIRED', message, subscription }`；前端收到后弹「开通会员引导」半屏 |
| P0-6 | `family.getMyFamily` 返回里追加 `subscription` 快照 | 参考 [数据模型.md §7](./数据模型.md#7-getmyfamily-返回订阅快照的字段建议) | 前端 `app.globalData.family.subscription` 可直接用 |
| P0-7 | 家庭页钥匙卡右侧加「会员」入口按钮（占位） | 未开通显示红色 NEW 角标；点击跳「会员敬请期待页」，展示权益对比表 + "即将上线" | 页面可进入，点击开通按钮显示「敬请期待 Toast」 |
| P0-8 | AI 浮窗 / 额度耗尽时加转化引导 | 免费版额度 ≤ 2 次时弹半屏卡片：「今日还剩 X 次，开通会员不限次」 | 用户点击「了解会员」进 P0-7 的占位页 |
| P0-9 | 云函数 `billing.getUsage(familyId)` 初版 | 返回当前家庭的 `{ aiCapture: {used, limit, period}, aiAssist: {...} }` | 占位页可用它展示真实剩余额度 |

### P0 验收要点

1. 连续 5 次用同一 openid 调 `ai.extract`（不带 BYOK），第 6 次被拒，次日放开。
2. 有 BYOK 的家庭即使免费版，调用次数不受 5 次限制。
3. 家庭页 / AI 入口的「会员」点击率能在埋点里被观测到（如果没埋点，先接微信小程序自带的分析事件）。

### P0 验收后需要做的决策

根据 P0 数据决定 P1 何时启动：
- 「AI V1 额度耗尽用户」比例 ≥ 15% → 立刻做 P1，付费意愿强；
- 家庭页「会员」入口点击率 ≥ 5% → 立刻做 P1，落地页流量够；
- 两个都低于 → 先优化 AI 识别体验 / 推 AI V2 出来，再启动 P1。

## P1 · 付费闭环（约 2 周）

> 目标：从「想买但买不了」变成「能真实付费到账」。  
> 上线后才有真实的收入数据，才能判断项目能不能自给自足。

### P1 任务清单

| T-ID | 任务 | 产出物 | 验收标准 |
|------|------|--------|----------|
| P1-1 | 建 `orders` 集合 + 索引（特别是 `transactionId` 唯一） | 控制台建好 | 参考 [数据模型.md §2.2 / §3.2](./数据模型.md#22-orders) |
| P1-2 | 选支付方案并申请能力 | 起步「方案 A：微信小程序虚拟支付」；拿到 `midas` / 商户号等配置 | 小程序端 `wx.requestMidasPayment` 文档示例 Demo 能跑通 |
| P1-3 | `cloudfunctions/billing.createOrder({ plan, period, promoCode? })` | 写 `orders(pending)` 并返回前端拉起支付所需参数 | 幂等：同一次点击重复触发不写多单；`amount / extendDays` 按套餐表计算 |
| P1-4 | 微信支付回调处理（或小程序端 `success` 回调 + 云函数二次确认） | `billing.wechatConfirm(transactionId, orderId)` → 查 `orders.transactionId` 唯一 → 调 `extendSubscription` → 写 `orders(paid, payAt, transactionId)` | 同一 transactionId 回调两次不会重复延长订阅（唯一索引保证） |
| P1-5 | `extendSubscription(familyId, plan, extendDays)` | 逻辑：读现有 `subscriptions`，`endAt = max(now, 当前endAt) + extendDays`，写回；若原 plan 更低则升级 plan | 免费升家庭、家庭续家庭、家庭提前升 premium 三种场景全部可回归 |
| P1-6 | 完成会员购买页 UI | 按 [方案.md §7.2](./方案.md#72-购买页信息结构按转化漏斗从上到下) 的结构实现；底部吸底大按钮拉起支付 | 成功支付后返回显示「开通成功，全家共享」，并把 `getMyFamily` 返回的 subscription 立即刷新 |
| P1-7 | 非户主进入会员页的引导 UI | 顶部显示「请联系家庭创建者开通」+ 创建者昵称（如空则「家人」）+ 一键复制话术 | 不显示购买按钮 |
| P1-8 | `cloudfunctions/ai/act` 接入门控（AI V2 上线时同步做） | plan=free 时看新用户 7 天是否还在 + 体验额度 20 轮是否用完；否则按 30 / 100 轮 / 家 / 天 限 | V2 新分包入口点进去就被拦截，跳会员页 |
| P1-9 | 家庭其它容量门控接入（可选 P1 后延到 P2） | `item.create` / `space.create` / `tag.create` / `family.join` 分别按上限拦截，并显示免费版上限提示 | 免费版 51 件物资被拒并显示「开通会员不限物资」 |
| P1-10 | `theme.updateBackground` 接入门控 | 非默认 5 套主题对免费版拦截，并引导「开通会员解锁全部 17 套」 | 免费版点 17 套里的某套会弹引导 |
| P1-11 | 续费到期提醒（先简单后复杂） | 在 `expireNotify` 同一个定时触发器里加逻辑：扫 `subscriptions.endAt` 在 7/3/1 天内的，给户主发微信订阅消息（需先申请订阅模板） | 到期前 7 天户主会收到提醒；点消息跳会员页续费 |
| P1-12 | 上线前的成本熔断补完 | 在 `checkEntitlement` 里加单日 200 次上限 + 单家庭月度模型成本 > ¥50 熔断 | 模拟触发后返回 `denied_circuit_breaker`，调用被拒 |

### P1 验收清单（真实走一遍）

1. **建家 → 默认 free**：新用户建家庭后，`getMyFamily` 返回 `plan: 'free'`。
2. **免费建满 50 件物资 → 第 51 件被拒（若 P1-9 做了）**。
3. **户主进会员页 → 买年卡 ¥98 → 支付成功**：`orders` 多 1 条 paid 记录，`subscriptions` 的 `endAt` + 365 天。
4. **支付成功后立刻调 `ai.extract` → 不再被 5 次 / 天限制**。
5. **回调幂等**：重复调用 `billing.wechatConfirm` 传入同一 transactionId，`subscriptions.endAt` 只延长一次。
6. **非户主点「开通会员」 → 看不到购买按钮，只看到「联系创建者」**。

### P1 上线后的关键观测

盯 7 天：
- 首单转化率（免费 AI 用户里多少人买了）；
- 退款率（> 5% 就说明权益描述有问题）；
- 会员首日激活后 3 天内是否实际调用了 AI 超过 10 次（没调用 = 没感受到价值，续费率会低）。

## P2 · 精细化运营（上线 1 个月后再做）

> 目标：拉长 LTV（用户生命周期价值），让会员从「买一次」变成「年年续」。  
> 前提是 P1 付费链路稳定、毛利润正。

### P2 任务分组（按价值从高到低）

#### 组 A · 提升续费率（价值最高）

| T-ID | 任务 |
|------|------|
| P2-A1 | 优惠券 / 兑换码系统：`promoCodes` 集合 + `billing.applyPromoCode`；场景如「过期未续费 7 天回归券 ¥30 OFF」「邀请好友开通赠送双方 30 天」 |
| P2-A2 | 邀请奖励：A 家庭户主邀请 B 家庭开通会员 → `extendSubscription(A家, +30 天)` |
| P2-A3 | 续费优惠：在 `endAt` 前 3 天内续费显示「立减 ¥10 专属优惠」按钮（前端 + billing 计算 amount） |
| P2-A4 | 会员到期后不降免费版立刻断，给 3 天「会员宽限期」，期间还能续上连续订阅折扣 |

#### 组 B · 继续做差异化权益（提升付费转化）

| T-ID | 任务 |
|------|------|
| P2-B1 | 导出物资 / 消息历史为 Excel：高级会员功能；新增云函数 `export.items(familyId)` / `export.activities(familyId)`，生成云存储文件返回下载链接 |
| P2-B2 | 自定义主题封面图：高级会员允许上传自定义图片当家庭封面（原来只允许 17 套预设色）；云存储独立目录，家庭配额 5 张 |
| P2-B3 | 更久的 AI 上下文窗口：调用 `ai.act` 时若 plan=premium，prompt 里额外拼最近 30 天 `activities` 摘要 + 常用物资模式 |
| P2-B4 | 高级模型切换：高级会员默认走更贵但更准的模型（如 DeepSeek-Reasoner），体现在 `modelCostFen` 和 `provider` |

#### 组 C · 数据看板与异常报警（防止亏钱 / 被刷）

| T-ID | 任务 |
|------|------|
| P2-C1 | `billing.dailyReport` 云函数，每天定时输出一份 JSON：DAU、AI 调用数、模型成本、订单数、金额、转化率、续费率、毛利；写入一个 `dailyReports` 集合 |
| P2-C2 | 超支报警：当日 `usageLogs` 中「模型成本分 × 家庭数」超过 ¥200 时，用云函数短信或企业微信通知你本人 |
| P2-C3 | 异常账号识别：某 openid 近 7 天被 `denied_quota` 超过 30 次 → 标记为「高付费意向」，前端弹出更激进的会员引导或赠送 1 天试用 |

#### 组 D · 自动化与合规（后期）

| T-ID | 任务 |
|------|------|
| P2-D1 | 接微信虚拟支付的「自动续费」能力（需单独申请），取消手写续费提醒 |
| P2-D2 | 退款后台：输入 `orderId` 调 `billing.refund` 走退款接口 + 在 `subscriptions` 里按比例回退 `endAt` |
| P2-D3 | 合规信息完善：会员页底部加「用户协议」「隐私政策」「自动续费规则」入口（审核被卡时必做） |

## 与其它 in-progress change 的对接顺序

根据 [`phase1-status.md`](../2026-09-17-phase1-status.md)，当前阶段 in-progress 有：

1. **AI V1 真机验收**（`packageAi`）→ 建议先完成，再接 `gatekeeper(aiCapture)`（P0-5）。不然接上门控后用户本来就用不了，无法验证付费转化。
2. **AI V2 助手落地**（`openspec/changes/ai-assistant-v2/`）→ 建议 **先上 V2 门控占位（P1-8 同批）**，V2 功能本身和「会员专享」的心智同步放出，转化率通常更高。
3. **用户体系（昵称 / 头像）** → 非阻塞，但 P1-7（非户主引导页）显示「请联系 <创建者昵称> 开通」比显示「请联系家人开通」转化率高 15~30%，建议 P1 前半做。
4. **搜索** → 完全不相关，可并行。

**推荐时间顺序**：
```
本周：AI V1 真机验收 + P0-1~P0-9 节流占位
↓
下一周：AI V2 功能实现（并行 P1-1~P1-5 支付侧）
↓
第三周：AI V2 上线 + P1-6~P1-12（会员购买页 + 容量门控 + 续费提醒 + 熔断）
↓
第四周起：观察 P1 数据，决定 P2 组 A / B / C 先做哪组。
```

## 不做清单（即使 P2 也先别碰）

- ❌ 个人订阅与家庭订阅并存（逻辑复杂，转化率提升不明显）；
- ❌ 点数 / 次卡 / 打包次数售卖（漏斗多了一层，转化反而降）；
- ❌ 分销返利（合规风险 + 税务麻烦）；
- ❌ 按角色差异化（免费版管理员只读、会员可写——和现有「全员同权」心智冲突，会流失用户）；
- ❌ 与 iOS/Android 做差异化价格（小程序平台审核会找事）；
- ❌ 接广告变现（家庭账本类场景广告体验极差，破坏品牌）。

## 最终交付形态的验收 Checklist

确认整个会员机制可交付、可长期维护时，按本表跑一遍：

- [ ] **集合层面**：`subscriptions` / `orders` / `usageLogs` 三张表结构完整，索引按 §3 全部建好；
- [ ] **安全规则**：三张表客户端写 deny；读权限仅 `orders` 对本人 openid 可读；
- [ ] **门控覆盖**：`family / item / space / tag / ai` 五个云函数的对应 action 都接入了 `checkEntitlement`；
- [ ] **支付闭环**：`createOrder → pay → confirm → extendSubscription` 全链路联调通过，回调幂等有测试；
- [ ] **BYOK 兼容**：自带 Key 的家庭在任何套餐下 AI 都不拦截、不计额度；
- [ ] **熔断保护**：单日 200 次 / 单家庭月度 ¥50 两道熔断触发过一次并验证；
- [ ] **UI 路径**：家庭页入口、AI 浮窗入口、额度耗尽报错页、非户主引导页四条路径都能跳会员页；
- [ ] **数据报表**：能按日输出 P1 上线后 §9 指标表（转化率、ARPU、模型成本、毛利）。
