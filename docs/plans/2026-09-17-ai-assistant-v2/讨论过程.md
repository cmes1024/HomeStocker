# 讨论过程（AI 助手 V2）

> 目录：[`README.md`](./README.md)  
> 定稿：[方案.md](./方案.md)  
> 本文只记录 **为什么这样选**。实现以方案为准。

讨论发生在 2026-09-17。起点是：第一阶段 AI 只落地了拍照录入向导，录入费劲、查改删仍靠手；怎样才能最大限度用 AI 管物资，同时交互比向导和半屏聊天更轻。

---

## 1. 先否定的两条主路径

对照现状：`packageAi` 是选图 → 打字（语音按钮未接上）→ 抽取 → 只读预览卡 → `item.create`；图不进模型；首页搜索栏仍是装饰；09-07 半屏对话未做。

讨论过三种产品形态：

| 路 | 结论 |
|----|------|
| A. 把现有向导做快（补视觉、预览可改） | 只加快入库，管不了查/用/挪 |
| B. 嵌进现有页面：搜索/随手记/详情短句，写库仍走现有云函数 | **采用，作为 V2 方向** |
| C. 09-07 半屏 Copilot + LangGraph | 天花板高，买菜入库和批量都慢；独立服务、流式后置 |

结论：**最大限度用 AI ≠ 做成聊天框。** 模型干认知，界面确认或直出结果。V2 先做自然语言文本助手，不复活 `pages/chat`。

---

## 2. 状态怎么喂给模型

一度想把「空间、位置、标签、全部物资和状态」每次都塞进 prompt。否决原因：物资常变、云开发分页、token 和「看漏中间」；也违反「不要为方便模型把货嵌进 `families`」。

中间方案是「目录常驻 + 按意图检索切片 + 工具循环」。担心卡在：模型分析出「往冰箱放牛奶」之后还要再查冰箱，调用次数多、流程易断。

收口成 **家庭树 = 配置骨架，不是库存副本**：

- 树里只有空间 → 位置、标签。
- 独立集合存储；结构写成功后同步，缺失或版本对不上则重绘。
- **物资增删改不改树。**
- 对照树能回答「有没有冰箱、有几台」。
- 「这台冰箱里有没有牛奶」最多再探一次物资接口。
- 禁止把树嵌进 `families` 文档。

现场每次 join 三张表也能拼出同样骨架；单独存树是为了 AI 入口稳定、同步合同明确，不是第二份真相。真相仍是 `spaces` / `locations` / `tags`。

---

## 3. 合并：点到为止

入账默认 **没说合并就新开**。全部处理完后用操作汇报提示「可能重复」；用户再说「合并掉」才是第二次。

合并需要单独能力和单独 prompt，**本讨论不再展开语义**（留谁、日期怎么揉等）。V2 能力表里 `item.merge` 占位且关闭。

---

## 4. 四步边界（中途改过一次场景切分）

曾对齐过「代码先 `route`，再跑 query / ingest / update / remove 各一份 prompt」。随后明确改成：

> 模型决定怎么做就怎么做，提供接口能力边界和现有状态给它。

因此：

1. **家庭树** — 结构快照，更新 / 重绘机制。
2. **Prompt 工程** — 不是一个万能人格，也不是代码先锁死场景；而是能力说明分节 + 计划格式。旧 `item-extract-v1` 不和新助手混用。
3. **新分包** — 理论上不影响手填表、清单、详情、V1 拍照向导。
4. **先不要语音** — 只支持自然语言文本。不接 `transcribe`、不上同声传译。

查 / 记 / 改 / 删仍是模型可选用的 **接口**，不是五个人格互斥。取消独立 `route` 云逻辑；一句里又查又记可以按序出多步计划。

---

## 5. 系统能力边界要能迭代

接口白名单如果只写在某一版 act prompt 里，加「合并」或关掉某能力时，prompt 和执行器会对不齐。

因此再加一层 **系统级能力表**（类似 `aiPrompts` 的 version 覆盖）：

- 渲染进模型的 `{{CAPABILITIES}}` 和执行器白名单读同一份。
- `enabled: false` 的能力不进 prompt。
- 代码硬底线挡住 `family.leave`、密钥等，即使库被改也不能执行。
- 应用级，不按家庭；家人不可改。
- 与家庭树分开：树随这家结构变，能力表随产品版本变。
