# 微信小程序新能力研究与设计约束

> 日期：2026-08 研究稿 | 状态：**参考约束，不是当前实施范围**（原 D 波「多用新能力」仍后置）  
> 现行产品范围见 [`plans/2026-09-17-phase1-status.md`](./plans/2026-09-17-phase1-status.md)。

---

## 1. 先说结论

你的意思我已经完全理解，而且这个方向是对的。

这类“家庭物资管理”小程序，本质上非常适合往微信官方的新技术能力上靠，尤其是：

1. `Skyline` 适合承担核心高频页面，提升滚动、转场、长列表和复杂交互的稳定性
2. `worklet` 适合承担拖拽、跟手、滑动关闭、手势联动、弹层过渡等“接近原生”的细节体验
3. `手势系统`、`自定义路由`、`共享元素`、`sticky-header`、`list-view`、`grid-view`、`page-container` 这些能力，应该一起考虑，而不是只盯着 `Skyline` 和 `worklet`
4. 后续设计不能再按“整页全局滚动 + CSS sticky/fixed + Web 风格弹窗 + 浏览器式层叠上下文”的习惯来做
5. 这个项目如果要追求“近原生甚至超过原生”的体验，**设计稿层面就必须体现出微信小程序的结构约束、交互结构和降级策略**

换句话说：

**不是把现有原型换个技术实现就够了，而是要从页面结构、导航模型、滚动模型、转场模型、弹层模型、列表模型上整体重构成微信小程序思维。**

## 2. 官方能力理解

## 2.1 Skyline 是什么

根据微信官方文档，`Skyline` 是小程序在 WebView 之外新增的渲染引擎，目标是提供更接近原生的渲染性能与交互体验。

它的重要意义不是“只更快一点”，而是：

1. 渲染线程与逻辑线程职责更明确，界面不容易被业务逻辑阻塞
2. 页面之间不再像多个 WebView 那样重，内存与切页成本更低
3. 长列表、滚动、原生组件同层、页面转场、手势动画这些问题，能有更自然的解决方式
4. 可以在页面级别混合使用 `Skyline` 和 `WebView`，适合渐进式迁移

对设计的直接影响是：

1. 可以放心设计更顺滑的滚动与过渡，而不是刻意保守
2. 可以设计更像原生应用的“半屏页 / 下沉页 / 联动转场 / 跟手返回”
3. 可以把复杂高频页面优先放到 `Skyline`，而不是要求整个小程序一次性全切

---

## 2.2 worklet 是什么

官方定义里，`worklet` 是一套可让动画逻辑运行在 UI 线程的机制，用来解决交互动画中跨线程延迟导致的卡顿、掉帧和不跟手问题。

它适合的不是普通淡入淡出，而是下面这些“用户对实时性很敏感”的动作：

1. 拖拽
2. 跟手滑动
3. 半屏弹层下滑关闭
4. 列表边界联动
5. 手势驱动的卡片位移、缩放、回弹
6. 转场过程中页面和元素的同步联动

对设计的直接影响是：

1. 后续原型里可以大胆设计“跟手”的交互，而不必局限在点击后播放一个普通过渡
2. 但这些交互必须是**明确可映射到手势系统 + worklet 动画**的，不能做浏览器式的模糊想象

---

## 2.3 这次不应只看 Skyline 和 worklet，还要一起看的能力

从微信官方文档看，真正组成“近原生体验”的不是一个点能力，而是一个组合：

1. `Skyline`
2. `worklet`
3. `手势系统`
4. `自定义路由`
5. `共享元素`
6. `scroll-view` 增强能力
7. `sticky-header`
8. `list-view`
9. `grid-view`
10. `page-container`
11. `wx.preloadSkylineView`

对设计来说，后面真正要落地的，其实是一整套“页面模型”。

## 3. 微信小程序模型下，后续设计必须遵守的结构约束

## 3.1 页面结构要从“整页滚动”改成“固定壳层 + 局部滚动”

官方文档明确建议在 `Skyline` 下使用**局部滚动**，不再依赖传统的页面全局滚动。

因此后续原型要默认采用下面的页面结构：

1. 自定义导航栏
2. 页面固定头部
3. 主内容区使用 `scroll-view`
4. 底部导航栏固定
5. 页面弹层、半屏页、操作面板单独建模

这意味着：

1. 不能再按“整页自然滚动”的网页思路画原型
2. 不能默认假设 `position: sticky`、`overflow: auto`、全局页面滚动能像浏览器一样工作
3. 物资列表、首页信息流、家庭管理页都应以局部滚动为设计前提

---

## 3.2 自定义导航栏要作为默认前提

官方兼容文档明确指出，切换到 `Skyline` 后不支持原生导航栏，推荐使用自定义导航，并在配置层使用 `navigationStyle: "custom"` 保持兼容一致。

所以后续设计必须默认：

1. 顶部导航栏自绘
2. 顶部标题、返回按钮、更多按钮、搜索入口、筛选入口，都放在自定义导航体系里
3. 不能再把系统导航行为当成默认存在

对当前项目尤其重要，因为：

1. 首页顶部有家庭切换主入口
2. 物资列表需要搜索、筛选、视图切换
3. 物资详情页需要返回、编辑、删除等操作
4. 家庭页可能需要右上角管理操作

这些都更适合统一收敛到自定义导航模型。

---

## 3.3 不能再按 Web 的 CSS 能力来设计

官方 WXSS 文档说明，`Skyline` 的样式能力是 WebView 的子集，而且有明显差异。

设计上必须注意：

1. 默认布局不是你熟悉的 Web 默认值，需要显式配置 `defaultDisplayBlock`、`defaultContentBox`
2. `inline` / `inline-block` 支持不完整，不能依赖复杂的行内排版技巧
3. 文本省略要优先通过 `text` 组件处理，不能把省略号方案建立在 `view` 上
4. `z-index` 不遵循完整 Web 层叠上下文，只在兄弟节点层级上更可靠
5. `overflow: scroll` 不能作为滚动方案，滚动应该交给 `scroll-view`
6. `position: fixed`、`absolute`、`sticky` 的思路都要谨慎，尤其是吸顶优先考虑 `sticky-header`
7. 不应依赖复杂属性选择器、浏览器式高级层叠技巧、多背景图、多重阴影等能力

这对原型风格的影响很大：

**视觉可以高级，但结构必须克制。**

也就是说：

1. 可以做高级的分层、动效、卡片和沉浸感
2. 但不能靠浏览器式 CSS 技巧去“硬凹”

## 4. 当前项目最值得使用的新能力

下面这些不是泛泛而谈，而是结合“家庭物资管理小程序”的具体场景给出的建议。

## 4.1 首页

### 推荐能力

1. `Skyline`
2. 自定义导航
3. 局部滚动 `scroll-view`
4. `sticky-header` 或分区吸顶
5. `wx.preloadSkylineView`

### 推荐原因

首页是高频入口，承载：

1. 当前家庭切换
2. 提醒看板
3. 快捷入口
4. 临期预览
5. 最近操作

这是典型的信息型首页，最容易出现：

1. 滚动中模块切换顿挫
2. 顶部操作区和内容区关系不清
3. 进入下一级页面时缺乏连贯感

### 设计建议

1. 顶部家庭切换区做成固定壳层的一部分，不跟内容区一起滚
2. 内容主区使用局部滚动
3. 临期提醒、待补货、最近操作等分组信息，可以在后续版本尝试吸顶分区头
4. 从首页进入“物资列表 / 物资详情 / 家庭切换面板”前，使用 `wx.preloadSkylineView` 做关键页预热

### 不建议

1. 整页长滚动 + 顶部用大量 `fixed` 叠层
2. 首页里堆很多复杂浮层同时共存

---

## 4.2 物资列表页

### 推荐能力

1. `Skyline`
2. `scroll-view type="list"`
3. `list-item`
4. `sticky-header`
5. `list-view`
6. `grid-view` 作为备选扩展
7. `共享元素`

### 推荐原因

物资列表是这个项目最典型的高频长列表场景。

官方文档明确指出：

1. `Skyline` 对长列表有按需渲染优化
2. `scroll-view` 的直接子节点是按需渲染粒度
3. 列表项可通过 `list-item` 参与样式共享

### 设计建议

1. 列表结构要为性能而设计，不要在 `scroll-view` 下再包一层大容器把所有列表项裹进去
2. 分类筛选、位置筛选、临期状态筛选，可以使用吸顶头部
3. 如果后续引入“按分类分组展示”，优先考虑 `sticky-header`
4. 从列表卡片进入详情页时，建议为商品主图、名称区块或关键卡片做 `共享元素`

### 适合做共享元素的对象

1. 物资缩略图
2. 物资名称卡片
3. 临期状态标签

这样从列表到详情会更像原生应用的 Hero 动画，而不是普通硬切页。

### 不建议

1. 列表项高度结构差异过大却强行塞进同一模式
2. 大量中间插入节点导致列表结构频繁重排
3. 用纯 CSS sticky 去实现复杂分组吸顶

---

## 4.3 物资详情页

### 推荐能力

1. `Skyline`
2. `共享元素`
3. `worklet`
4. `自定义路由`

### 推荐原因

详情页是最适合做“原生感”升级的地方，因为它通常来自列表点击，用户对转场连续性敏感。

### 推荐设计方向

1. 列表卡片进入详情，采用共享元素过渡
2. 详情页进入时不仅是页面位移，还可以让卡片头图 / 标题区参与共享元素动画
3. 如果详情里未来增加图片预览、库存调整面板、二级操作面板，可以用 `page-container` 或半屏路由处理

### 特别适合 worklet 的细节

1. 库存调节按钮按下反馈
2. 顶部头图 / 重点卡片随滚动轻微联动
3. 下拉关闭图片预览或半屏详情

---

## 4.4 添加 / 编辑物资页

### 推荐能力

1. `Skyline`
2. `page-container`
3. `自定义路由`
4. `worklet`

### 推荐原因

录入流程通常会涉及：

1. 拍照识别
2. 扫码
3. AI 预填
4. 纠错确认
5. 选择分类、位置、提醒方式

这些很适合做成“主表单页 + 局部半屏面板 / 假页”的结构。

### 设计建议

1. 分类、位置、提醒设置，优先设计为页内半屏面板，而不是浏览器式下拉菜单
2. OCR 识别结果确认，可考虑做成“从底部上来的确认层”或者独立半屏子页
3. 对于“拍照后回填表单”的过程，不应设计成复杂弹窗堆叠

### page-container 的价值

官方文档指出，`page-container` 的核心价值是：

用户返回时，优先关闭容器而不是离开当前页面。

这非常适合：

1. 分类选择
2. 位置选择
3. OCR 识别确认
4. 编辑提醒策略

它更符合微信小程序用户的心理预期。

### 要注意

1. 一个页面当前最多只有 `1` 个容器
2. 所以后续设计不能同时堆多个 page-container 级别的假页

---

## 4.5 家庭页 / 家庭列表管理

### 推荐能力

1. `Skyline`
2. `scroll-view`
3. `page-container`
4. `自定义路由`
5. `worklet`

### 推荐原因

家庭页里存在两类很适合做成微信式近原生体验的交互：

1. 家庭切换
2. 家庭管理动作面板

### 推荐设计方向

1. 首页顶部点击家庭切换时，不一定非要进入完整新页，可以设计为页内半屏“家庭切换面板”
2. 家庭列表中“新增 / 编辑 / 删除”操作更适合进入半屏管理态，而不是 Web 式 dropdown
3. 家庭成员管理和角色调整，后续也更适合半屏页或二级假页

### 适合 worklet / 手势系统的场景

1. 家庭切换面板下拉关闭
2. 半屏管理页跟手下滑关闭
3. 家庭卡片按压反馈与回弹

---

## 4.6 图片预览 / 海报 / 分享图

### 推荐能力

1. `snapshot`
2. `page-container`
3. `共享元素`

### 推荐原因

虽然你当前项目主线还不是内容分享，但这个产品很适合未来扩展：

1. 临期提醒海报
2. 家庭囤货清单分享图
3. 采购建议分享图

官方文档提到，`Skyline` 对 WXML 子树截图更友好，这意味着以后如果做分享图，可以优先采用更接近页面真实结构的方式，而不是完全靠 canvas 手工绘制。

可以后续再看是否上 `Skyline` 的：

3. 极少访问的后台设置页

## 6. 必须纳入设计稿的“近原生交互能力”

后续如果我要帮你改原型，我会把这些能力明确写进页面设计，不会只在备注里提一句“技术可实现”。

## 6.1 页面转场

适合加入设计的转场：

1. 列表卡片进入详情：共享元素
2. 首页进入家庭切换：底部弹起的半屏路由
3. 家庭管理进入编辑：半屏页推进
4. 图片 / OCR 结果 / 选择器：页内假页或半屏面板

## 6.2 跟手交互

适合加入设计的跟手交互：

1. 半屏页下滑关闭
2. 图片预览下滑关闭
3. 局部卡片横向轻扫操作
4. 列表边界和面板拖动的衔接

## 6.3 列表高级体验

适合加入设计的列表体验：

1. 吸顶筛选头
2. 按分类 / 临期状态分区吸顶
3. 长列表按需渲染友好结构
4. 列表卡片进入详情的连续过渡

## 7. 设计时必须避开的坑

这一部分非常重要，后续原型如果不避开这些坑，就会看起来高级，但落地时会反复返工。

## 7.1 Skyline 结构层面的坑

1. 不能默认依赖全局页面滚动
2. 不要把滚动区设计成一整页自然流文档
3. 不要默认系统导航栏存在
4. 不要设计多个复杂弹层长期叠加在同一页
5. 不要过度依赖 Web 的层叠上下文

## 7.2 WXSS / 布局层面的坑

1. 不要依赖复杂 `inline` 布局组织核心信息
2. 不要把文本省略设计在 `view` 上
3. 不要把 `sticky` 设计默认建立在 CSS sticky 上
4. 不要大量用 `position: fixed` 去补结构问题
5. 不要把复杂层级关系建立在大量 `z-index` 之上
6. 不要把滚动设计建立在 `overflow: scroll/auto` 思维上

## 7.3 worklet 层面的坑

官方文档里明确提到以下注意事项，后续交互设计要考虑它们：

1. `worklet` 只在 `Skyline` 下可用
2. 开发工具里要开启 `编译 worklet` 相关选项
3. `worklet` 里访问普通 JS 方法，需要 `runOnJS`
4. 页面方法需要 `bind(this)`
5. 外部对象会被冻结，不能按普通 JS 闭包思维去想
6. 不适合把复杂业务逻辑直接塞进 worklet

对设计的启示是：

**worklet 更适合驱动状态、位移、透明度、缩放、回弹，不适合承载复杂业务判断。**

## 7.4 手势系统层面的坑

1. 手势组件是虚组件，不参与布局
2. 只能有一个直接子节点
3. 不会像普通 touch 那样冒泡
4. 和 `scroll-view` 一起用时容易有手势冲突
5. 如果要实现列表滚动与面板拖动衔接，需要设计时就预留“手势协商”模型

这意味着：

1. 交互设计图里要明确谁接手手势
2. 不能只画一个“用户上下滑动，系统自己判断”的模糊动作

## 8. 对当前“家庭物资管理小程序”的设计修正建议

结合现有 PRD 和原型，后续我建议做下面这些修正。

## 8.1 首页

### 设计修正

1. 重新定义为“自定义导航 + 主内容滚动区 + 底部导航”
2. 家庭切换入口固定在顶部壳层
3. 提醒总览、快捷入口、临期列表、最近操作都放进局部滚动区
4. 如果后续内容增长，考虑吸顶筛选或吸顶信息条

### 体验升级点

1. 进入家庭切换使用半屏页
2. 首页进入详情使用共享元素
3. 首页首屏关键跳转做 Skyline 预加载

## 8.2 物资列表

### 设计修正

1. 明确长列表结构
2. 筛选条不要按 Web 顶部粘住思路做，优先按吸顶容器建模
3. 列表项结构要标准化，方便样式共享与按需渲染

### 体验升级点

1. 列表卡片进入详情做共享元素
2. 以后若做分类分组，可引入 sticky-section / sticky-header

## 8.3 详情页

### 设计修正

1. 顶部头图、主信息区作为共享元素候选
2. 编辑、删除、库存调整作为明确的操作区块
3. 图片预览、备注编辑等未来增强功能以半屏假页优先考虑

## 8.4 家庭切换与家庭管理

### 设计修正

1. 家庭切换不一定非得是完整新页
2. 更适合设计成底部弹起的家庭切换层
3. 创建/编辑/删除家庭，采用页内半屏假页或半屏路由

### 体验升级点

1. 下滑关闭
2. 卡片按压反馈
3. 当前家庭切换后首页数据平滑更新

## 8.5 添加 / 编辑物资

### 设计修正

1. OCR 结果、分类选择、位置选择、提醒策略，都应按“面板型交互”建模
2. 不要设计成很多下拉框和浮窗在一个页面里乱飞

---

## 9. 推荐的设计策略

如果目标是“近原生甚至超过原生体验”，我建议后续设计遵循下面的策略。

## 9.1 设计策略总则

1. 关键路径优先 `Skyline`
2. 滚动统一局部化
3. 顶部导航统一自定义
4. 长列表统一采用 Skyline 友好结构
5. 转场和半屏页作为主要体验升级点
6. 交互设计时同步考虑降级到 WebView 的朴素体验

## 9.2 体验策略总则

1. 动画要强调“跟手、连续、低负担”
2. 不追求炫技型动效
3. 优先改造用户高频路径
4. 先把切换、浏览、录入、编辑这四类动作做顺

---

## 10. 后续我建议怎么推进

如果你认可这份研究结论，下一步我建议按下面顺序继续。

### 第一步：先修设计模型

我先把现有原型整体改成微信小程序模型：

1. 自定义导航
2. 局部滚动
3. 半屏页 / 假页结构
4. Skyline 友好的列表和页面层次

### 第二步：再把“新能力”显式写进原型

我会在原型里明确体现：

1. 哪些页面是 Skyline 关键页
2. 哪些跳转有共享元素
3. 哪些面板是半屏页
4. 哪些关闭动作是手势驱动
5. 哪些列表设计是为 `scroll-view type="list"` / `sticky-header` / `list-view` 预留的

### 第三步：再反推 PRD 和研发约束

我会把这套能力同步回文档，形成：

1. 设计约束
2. 页面结构约束
3. 技术落地建议
4. 降级策略
5. 高风险踩坑清单

## 11. 本轮研究结论

一句话总结：

**这个项目完全可以朝微信官方“近原生”路线升级，但前提不是简单套用新技术名词，而是从现在开始，把原型和交互模型都严格建立在微信小程序的页面结构、滚动结构、导航结构、转场结构和手势结构之上。**

这也是后续我给你改原型时会坚持的方向。
